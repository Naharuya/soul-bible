경쟁 서비스의 정책 문구나 저작권 승인을 복사하지 않았다. ONARIA의 실제 처리 구조와 운영자의 확정 정보가 별도로 필요하다.

## 구현

- **회원정보:** 신규 등록 화면에서 이름·전화번호·교회명 입력을 제거하고 런타임 signup을 중단. 기존 등록자에게 앱/웹 삭제 요청 안내 제공. 관리자 세션·HTTPS·CSRF·정확한 대상 재확인·외부 본인 확인 기록 번호가 있어야 단일 회원 삭제 가능. 전화번호만 입력해서 타인 데이터를 삭제하는 공개 API는 만들지 않았다.
- **개인정보:** `backend/config/privacy-policy.json`은 승인 대기. 운영자·문의처·보관·국외 이전·검토자 등을 검증하고 `ready` 계산. 승인되지 않은 운영 정책은 일반 대화를 503으로 거절. 정책 버전 동의가 없으면 428. 위기 입력 처리는 이 검사보다 먼저 실행된다. 앱은 안내 확인 및 동의 전 대화 전송을 중단하고 철회를 지원한다.
- **신고:** `/v1/reports`에 사유와 중복방지 ID 전송. AI 응답 첨부는 기본 해제, 명시적으로 선택한 경우만 최대 3,000자. 사용자 질문이나 전체 대화를 자동 첨부하지 않는다. 승인된 보관 기간을 가진 SQLite 저장소, 재시도 중복 방지, 검토 상태, 만료 정리, 관리자 no-store와 로그아웃 후 화면 제거 구현. 평점/카테고리 `/v1/feedback` 계약은 보존하며 기존 집계는 메모리 기반이다.
- **자료:** 번들 15개 모두 pending. NIV 영어 본문 14개 제외. Release에서는 검토자·날짜·사용권 근거·본문 SHA-256이 맞는 approved 자료만 노출. 한국어 KRV 표시 자체가 사용권 확보를 의미하지 않는다. 현재 Release의 말씀 자료는 비어 있으므로 공개 배포 불가.
- **통합:** origin/main `e58a0a8...`을 포함한 기존 통합 커밋 `5031a81...` 위에 작성. 앞선 충돌 해결과 파서·Safety 수정 유지. 기존 서명 키·package·API 유지. 배포 ZIP에 정책 설정을 포함시키고 Cafe24 artifact 생성 전에 개인정보/자료 승인을 검사하도록 추가했다.

신규 회원 수집 중단은 출시 범위에 대한 응답 전 임시 후보 기본값이다. 향후 회원 서비스를 다시 열려면 로그인 발급·소유자 인증·삭제·동기화·보관 정책을 먼저 완성해야 한다.

## 승인과 실제 운영에서 남은 일

1. 실제 운영 주체명, 공개 문의 이메일, 회원/사용량/신고 보관 기간, AI 제공자별 이전 국가·항목·목적·시기·방법·보관·거부 방법을 확정한다. 한국 개인정보 법률 적용 검토 및 스토어 선언과 대조한다. 현재 자유 서술 필드는 이를 대신 검증하지 않는다.
2. 정책 검토자는 문구와 실제 저장/전송/로그/백업을 대조한 뒤에만 승인한다. 정책 내용이 달라지면 버전을 바꾸어 재동의를 받는다. 문의처가 준비되지 않으면 기존 회원 삭제 요청은 접수 가능한 상태가 아니다.
3. 자료별 번역·출처·권리자·사용 허가 범위·출처 표기·검토자 승인을 확보한다. 본문을 확인한 후 해시를 고정한다. 일반 production registry와 기독교 pilot의 별도 승인도 필요하다. 이번 번들 검사는 RAG corpus 승인을 대신하지 않는다.
4. 관리자 삭제의 본인 확인은 외부 절차다. 확인 전에는 삭제 버튼을 사용하지 않는다. 확인 기록 번호는 API에서 형식만 검사하고 저장하지 않으므로 접근 제한된 운영 기록에 대상·승인·처리 결과를 별도로 관리해야 한다. 민감한 증빙을 Git/채팅/로그에 넣지 않는다. 백업에 남은 정보의 만료와 복구 시 재삭제, 법정 보존 예외를 별도로 검증한다. SQLite 행 삭제 성공은 모든 백업의 영구 소거를 의미하지 않는다.
5. 신고 담당자·검토 주기·처리 기준을 정하고 운영 신고 접수→관리자 확인→콘텐츠 개선을 종단 검증한다. 검토 완료 표시만으로 콘텐츠가 수정되지는 않는다. 신고는 최대 10,000개 저장하며 최근 100개를 화면에 표시한다. 대량 누적 전 운영 처리량/알림을 검증해야 한다.
6. 최종 SHA의 CI 확인 후 승인된 artifact로 운영 반영한다. 이번에는 서버 재시작, DB 변경, 실제 회원 삭제, 유료 API 호출, 마켓 제출을 하지 않았다. 정책 미승인 상태의 배포는 정상 대화를 막으므로 금지한다.
7. 실제 휴대폰·iOS 서명 archive/TestFlight·운영 Safety 관측·백업 복원·결제/권한·콘솔 선언 검증은 별도로 남아 있다.

## 증거

이번 실행은 `qa-store-candidate/` 로그를 참조한다. 이전 `STORE_READINESS_2026-09-15.md`와 `qa-2026-09-15/`는 원래 작업 트리의 과거 감사 기록이며 이번 후보의 검증 결과로 재사용하지 않는다. CI/빌드/최종 커밋 결과는 별도 실행 결과 파일에 기록한다.

## 회귀 중 발견해 수정한 사항

- 관리자 신고 목록을 모든 화면에서 조회하던 경로를 신고 화면으로 제한했다. 전체 브라우저 trace에서 관측된 429를 근거로 수정했으며 서버 요청 제한을 완화하지 않았다.
- 미승인 자료를 숨겼을 때 기존 저장 말씀 ID를 걸러내던 경로를 수정했다. 자료 목록이 비어도 ID는 보존하고, 자료 승인 후 다시 연결한다. 다른 기록을 저장한 뒤에도 복원되는 회귀 테스트를 추가했다. 비공개 자료의 본문은 표시하지 않는다.
- Android 컴파일과 동시에 수행한 전체 접근성 검사는 한 차례 60초 시간 초과가 있었다. 최종 브라우저 결과는 빌드 후 단독 재실행 로그로 구분한다.
- 브라우저 테스트의 공유 로컬 IP 때문에 서로 다른 테스트의 요청 제한 집계가 합쳐지는 문제를 확인했다. 격리 서버만 loopback proxy를 신뢰하고 브라우저 테스트마다 별도의 합성 IP를 사용하도록 수정했다. 운영 설정·240회 제한은 그대로이며 실제 요청 제한 검사는 backend suite에서 수행한다.

출시 차단은 코드 테스트 실패와 별개다. 정상 대화·자료 공개를 재개할 정책/권리 승인이 아직 없으므로 자동 검증 통과만으로 공개 출시할 수 없다. APK/AAB 파일 해시는 `qa-store-candidate/artifacts.json`, 소스 해시는 `qa-store-candidate/source-manifest.json`을 참조한다. 빌드의 기존 Kotlin 플러그인 향후 호환 경고는 별도 유지보수 항목이다.

이 후보는 draft PR용이다. 원격 CI는 새 커밋 SHA로 별도 확인하며, 이전 main의 성공 결과를 이 후보의 성공으로 취급하지 않는다. 운영 반영 전에 실제 개인정보 정책·자료 승인, 기존 회원의 본인 확인 운영 절차, 백업 및 복구, 운영 Safety 관측과 실기기 검증이 필요하다.
